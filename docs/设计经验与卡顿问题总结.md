# 漫画风 Redesign 设计经验与卡顿问题总结

## 一、项目背景

对原有 SchoolStore 校园电商平台进行整体视觉 redesign，将风格从普通现代风改造为 **Manga / Neobrutalism（漫画/新粗野主义）** 风格。涉及约 **56 个 Vue 组件** 的样式改造，覆盖首页、登录、商品详情、订单、用户、搜索、发布商品等全流程页面。

## 二、Manga / Neobrutalism 设计规范

### 2.1 设计语言

| 设计要素 | 规范值 | 说明 |
|---------|--------|------|
| 标题字体 | `'Black Han Sans', 'Courier New', monospace` | 粗黑体，厚重有力，无衬线 |
| 正文字体 | `'Noto Sans SC', sans-serif` | 清晰可读的中文无衬线体 |
| 边框 | `3px solid black` | 粗边框是 Neobrutalism 标志性特征 |
| 阴影 | `6px 6px 0 black` | 纯色偏移阴影，无模糊，硬朗 |
| 背景色 | `#fff` 纯白 | 大面积留白，突出内容 |
| 主色调 | `#000` 纯黑 | 黑白对比强烈 |
| 强调色 | 原色保留 | 不添加多余色彩 |
| 圆角 | `0` | 无圆角，直角硬边 |
| 按钮悬停 | `translate(-2px, -2px)` 上移 + 阴影缩小至 `3px 3px 0` | 按压感 |

### 2.2 排版规范

- 标题使用 `skewX(-20deg)` 斜切，增加漫画感
- `letter-spacing: 2.4px` 宽松字距
- 大号标题与内容之间的留白
- 使用 `::before` 伪元素做装饰线，替代传统分割线

### 2.3 响应式方案

- 使用 `[data-device="mobile"]` 属性选择器区分移动端
- CSS 变量体系集中控制：`--direction`, `--columns`, `--gap`, `--btn-scale` 等
- 移动端：列数减半、间距缩小、按钮缩小至 0.92 倍
- 不使用 CSS media queries，由 JS 在 App 层控制 `data-device` 属性

### 2.4 全局 CSS 变量

```css
:root {
  --direction: row;
  --direction-wrap: row;
  --direction-nav: row;
  --columns: 4;
  --columns-sm: 3;
  --gap: 60px;
  --gap-sm: 20px;
  --show-desktop: flex;
  --show-mobile: none;
  --base-font: 16px;
  --btn-scale: 1;
}
```

## 四、卡顿问题深度分析

### 4.1 问题现象

用户反馈："页面卡死"、"菜单栏上下滑动卡死"、"盲盒倒计时刷新时间卡死"、"热门好物滑动有bug"

### 4.2 根因一：粒子钟（patticleClock.vue）— 性能杀手

**文件**: [patticleClock.vue](file:///c:/Users/sound/Desktop/SchoolShopping/前端/school_shop_vue/src/views/Layout/component/patticleClock.vue)

**原始版本逻辑**（正确的）：
- `requestAnimationFrame` 持续循环，每帧清空画布 + 绘制所有粒子
- `setInterval` 每 1 秒调 `updateParticlesTargets()`：
  - `getImageData()` 读取全画布像素（同步阻塞操作）
  - 采样粒子点，对比上一次的文字内容
  - 调整粒子数组，分配新目标位置
- 粒子数量、`sampleGap`、`shadowBlur` 根据画布面积自适应

**错误改动**（导致卡死）：
1. **IntersectionObserver + visibilitychange** → 增加了两个额外的事件监听和状态变量（`isVisible`、`isPageVisible`）
2. **条件跳过绘制** → 虽然跳过了 `draw()`，但 `requestAnimationFrame` 依然在空跑，CPU 占用 100%
3. **`sampleGap` 从 3/4/5 改为 4/5/6** → 粒子采样变稀，视觉质量下降
4. **`shadowBlur` 从 `size*2.5` 降为移动端 `size*1.2`/桌面 `size*2`** → 模糊半径减少不影响性能，但视觉变丑

**关键教训**：`requestAnimationFrame` 的回调即使不绘制，只要它在持续递归调用自身，CPU 就不会降低。加条件检查跳过绘制但继续递归，**比不跳过更浪费**——因为你多做了条件判断的工作，而绘制工作本身没省掉多少。

**性能消耗本质**：
- `getImageData(0, 0, canvas.width, canvas.height)` 是**同步阻塞操作**，读取整个 canvas 的像素数据
- 每 1 秒执行一次，canvas 越大越慢
- 粒子数量 = 采样像素点 = canvas 面积 / sampleGap²，`sampleGap=3` 时粒子约 8000-15000 个，每帧全部更新位置 + 绘制

### 4.3 根因二：菜单栏（headerCom.vue）— overflow 冲突

**文件**: [headerCom.vue](file:///c:/Users/sound/Desktop/SchoolShopping/前端/school_shop_vue/src/views/Home/component/headerCom.vue)

**原始版本逻辑**（正确的）：
```javascript
tl = gsap.timeline({ paused: true })
  .to(expandedMenu.value, {
    duration: 1.2,
    delay: 0.1,
    height: 'auto',
    ease: 'power4.out'
  })
  .to(glassElements, {
    duration: 1,
    opacity: 1,
    ease: 'power4.inOut',
    stagger: 0.05
  }, 0.3)
  .reverse()
```
- 使用 `height: 'auto'` 让 GSAP 自动计算目标高度
- 初始 `.reverse()` 使时间线处于反向状态（菜单收起）
- `toggleMenu` 用 `tl.reversed(!tl.reversed())` 切换
- **CSS 无 overflow 限制**，GSAP 完全控制 height

**错误改动**（导致卡顿）：
1. **加了 `overflow-y: auto` + `max-height: calc(100vh - 60px)`** → GSAP 在动画 `height` 到 `auto` 时与 CSS 的 `overflow-y: auto` 冲突，浏览器需要不断重排（reflow）
2. **`onComplete` 切换 overflow** → 逻辑复杂化，增加了判断分支

**关键教训**：GSAP 的 `height: 'auto'` 会自动获取元素的 scrollHeight 作为目标值，此时**元素不能有 overflow 限制**。任何在 CSS 中设置的 `overflow` 都会干扰 GSAP 对 `height` 的动画计算。

### 4.4 根因三：热门好物（shopShowListCom.vue）— ScrollTrigger 错误配置

**文件**: [shopShowListCom.vue](file:///c:/Users/sound/Desktop/SchoolShopping/前端/school_shop_vue/src/views/Layout/component/shopShowListCom.vue)

**原始版本逻辑**（正确的）：
```javascript
scrollTween = gsap.to(pinWrap, {
  scrollTrigger: {
    trigger: sec,
    pin: sec,
    start: 'center center',
    end: () => `+=${pinWrapWidth}`,
    scrub: true,
    invalidateOnRefresh: true,
    onRefresh: refresh,
  },
  x: () => -horizontalScrollLength,
  ease: 'none',
})
```
- `start: 'center center'` — 当滚动区域的中心到达视口中心时触发
- `scrub: true` — 将动画与滚动条位置绑定

**错误改动**（导致回到顶部）：
1. **`start: 'top top'`** → 当滚动区域顶部到达视口顶部时立即触发 pin，还没滚动到热门好物区域就被强制 pin 住
2. **`scrub: 0.5`** → 增加延迟阻尼，与页面自然滚动冲突
3. **`fastScrollEnd: true`** → 快速滚动结束时的加速行为改变了原生滚动体验
4. **IntersectionObserver enable/disable** → 在可见/不可见时切换 ScrollTrigger 的启用状态，**每次重新启用都会触发位置重算，导致页面跳跃**
5. **`overscroll-behavior: contain`** → 阻止了浏览器的滚动链行为，破坏了页面整体滚动
6. **水平滚动限幅 `window.innerWidth * 0.8`** → 限制了热门的滚动距离，导致内容展示不完全

**关键教训**：ScrollTrigger 的 `start` 参数极其敏感：
- `'top top'` = 紧贴视口顶部触发，适合全屏 section
- `'center center'` = 居中触发，适合页面中间的横向画廊
- `'top bottom'` = 区域底部进入视口时触发（延迟触发）

### 4.5 根因四：新鲜好物（newProCom.vue）— IntersectionObserver 误用

**文件**: [newProCom.vue](file:///c:/Users/sound/Desktop/SchoolShopping/前端/school_shop_vue/src/views/Layout/component/newProCom.vue)

**改动内容**：
```javascript
visibilityObserver = new IntersectionObserver((entries) => {
  if (cardContainer.value) {
    cardContainer.value.style.animationPlayState = entries[0].isIntersecting ? 'running' : 'paused'
  }
}, { threshold: 0.1 })
```

**问题**：CSS 3D 动画 `autoRun3d` 使用 `perspective(800px) rotateY()` 配合 `translateZ(280px)`，本身性能消耗不大。`animationPlayState` 的切换虽然不会导致卡死，但频繁的暂停/恢复会让 3D 动画的位置重置，用户会感知到卡顿。

**注意**：3D 动画的 `will-change: transform` 已经做了正确的 GPU 合成层优化，不需要额外干预。

## 五、本次教训总结

### 5.1 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **不要动稳定运行的 JS/动画逻辑** | 如果原始版本的动画流程经过验证是流畅的，只需要改 CSS 样式即可 |
| 2 | **GSAP + overflow 不兼容** | GSAP 动画 `height` 时元素必须 `overflow: hidden`，否则动画计算会与 CSS 布局冲突 |
| 3 | **requestAnimationFrame 的空跑问题** | 一旦启动 rAF 递归，即使条件跳过绘制，CPU 也不会降低。要么完全停止（`cancelAnimationFrame`），要么让它跑 |
| 4 | **ScrollTrigger 的 start 值是双刃剑** | 改一个参数（`center center` → `top top`）就可能彻底破坏滚动行为 |
| 5 | **IntersectionObserver + ScrollTrigger 不要混用** | ScrollTrigger 自身已经管理了滚动触发和性能优化，再加一层 IntersectionObserver 会导致状态冲突 |
| 6 | **canvas getImageData 是阻塞操作** | 在每 1 秒的定时器里读取全画布像素，canvas 分辨率越大消耗越高。用 `sampleGap` 控制采样密度是正确的做法，不应改动 |

### 5.2 正确的工作流

```
用户原始版本（已优化） 
    → 只改 CSS（颜色、边框、阴影、字体、间距） 
    → 不改 JS（不变动画参数、不增事件监听、不改触发逻辑）
    → 测试验证
```

### 5.3 错误的工作流（本次踩坑）

```
用户原始版本（已优化）
    → 改 CSS ✓
    → 改 JS ✗ （加 IntersectionObserver、改 ScrollTrigger 参数、改动画逻辑）
    → 引入性能问题 + 滚动 bug
    → 需要 git reset 恢复
```

### 5.4 关于 GSAP 动画的最佳实践

1. **`tl.reversed(!tl.reversed())`** 比 `tl.play()` / `tl.reverse()` 更简洁，且无需记录当前状态
2. **`height: 'auto'`** 在 GSAP 中会自动获取 scrollHeight，但元素必须**无 CSS overflow 限制**
3. **`stagger`** 是让多个元素依次动画的强大参数，适合菜单卡片列表
4. **GSAP timeline 默认是正向**（`paused: true` 时不播放），`reverse()` 可以让它反向
5. 组件卸载时务必 `tl.kill()` / `scrollTrigger.kill()`，防止内存泄漏

### 5.5 关于 ScrollTrigger 的最佳实践

1. **`start: 'center center'`** 适合页面中间区域的横向滚动
2. **`scrub: true`** 是最流畅的绑定方式（非数值）
3. **不要混用 IntersectionObserver**，ScrollTrigger 自身已经做了性能优化
4. **不要在 pinned 元素上设置 `overscroll-behavior: contain`**，它会破坏整体的滚动链
5. **`end: () => '+=...'`** 使用函数动态计算，确保内容变化后能自适应

## 七、后续建议

1. **CSS 变量集中管理**：将设计 token（颜色、字体、间距、阴影等）放在 `App.vue` 的 `:root` 中，全局引用
2. **JS 类不动原则**：如果需要调整动画，只动 CSS 动画参数（duration、delay、keyframes），不动 JS 动画逻辑
3. **性能监控**：对于 canvas 粒子、ScrollTrigger、3D transform 等高消耗功能，保持原始作者的优化策略
4. **增量改造**：每次只改一个组件，改完立刻运行验证，不要批量修改后统一验证
